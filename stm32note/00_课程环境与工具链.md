## 核心概念

### 知识地图

| 名词 | 工程含义 | 常见位置 |
|------|----------|----------|
| MDK / Keil5 | ARM 嵌入式工程 IDE，负责编译、链接、下载和调试 | `[4-1]` 到 `[4-5]` |
| Pack / 芯片包 | MDK 识别 STM32 型号、启动文件、外设头文件所需的软件包 | MDK Pack Installer |
| DAP / CMSIS-DAP | ARM 标准调试下载接口，常用于 SWD 下载和单步调试 | `[3] [4-5]` |
| SWD | Serial Wire Debug，两线调试接口，常用 SWDIO/SWCLK | 核心板调试口 |
| 串口下载 | 通过 STM32 系统 Bootloader 和 USART 下载程序 | `[3]` |
| BOOT0 | 启动模式选择脚，决定从 Flash 还是系统存储器启动 | 核心板跳线/按键 |
| USB-TTL | 把电脑 USB 转成 UART TTL 电平，用于串口下载或串口调试 | `[3]` |
| STM32CubeMX | 图形化配置芯片、引脚、外设并生成初始化工程 | `[5-1]` 到 `[5-3]` |
| HAL 库 | ST 提供的硬件抽象层，CubeMX 生成工程时会引用 | `[5-3]` |
| `.uvprojx` | MDK 工程文件 | MDK 工程目录 |
| `.ioc` | CubeMX 配置文件 | CubeMX 工程目录 |
| `.hex` / `.bin` | 可下载到芯片的固件镜像 | MDK 输出目录 |
| `.axf` | 带调试信息的 ARM 可执行文件 | MDK 输出目录 |

### 常用 HAL API

本章重点是工具链，不是外设代码。最常见的 HAL 入口只用于环境验证：

| API / 宏 | 作用 | 常见用法 |
|----------|------|----------|
| `HAL_Init()` | 初始化 HAL 库和默认时基 | `main()` 开头 |
| `SystemClock_Config()` | 配置系统时钟 | CubeMX 生成 |
| `HAL_Delay()` | 毫秒延时，验证 SysTick 是否工作 | 简单测试 |
| `HAL_GPIO_TogglePin()` | 翻转 GPIO，验证程序是否运行 | LED 测试 |

## 本质理解

这几节课不是在学某个外设，而是在搭一条最小工程链路：

```text
硬件能上电
-> 电脑能识别下载器或串口
-> MDK 能编译工程
-> 下载器能把程序写进芯片
-> CubeMX 能获取 HAL 库并生成工程
-> 我知道代码该写在哪里、出问题该查哪一层
```

我现在把工具链理解成“把想法变成芯片里可运行程序的一条流水线”。MDK 负责把 C 代码编译成芯片能执行的机器码，DAP/SWD 或串口下载负责把机器码写进芯片，CubeMX 负责把重复的初始化代码先生成出来。

## 工作流程 / 原理

### 开发链路

```text
课程资料 / 官方安装包
-> 安装 MDK
-> 安装 STM32F1 芯片包
-> 连接核心板和 DAP / USB-TTL
-> 打开示例工程或 CubeMX 生成工程
-> 编译
-> 下载
-> 复位运行
-> Debug 单步或串口观察现象
```

### DAP 下载和串口下载的区别

| 项目 | DAP / SWD 下载 | 串口下载 |
|------|----------------|----------|
| 接口 | SWDIO、SWCLK、GND、3V3/VTref | USART TX/RX、GND、BOOT0 |
| 是否支持单步调试 | 支持 | 通常不支持 |
| 是否依赖 BOOT0 | 通常不依赖 | 依赖进入系统 Bootloader |
| 常见用途 | 日常开发、断点、变量观察 | 下载器不可用时的备用下载方式 |
| 常见问题 | 驱动、Debug 选择、Connect 模式 | BOOT0、TX/RX 接反、波特率/串口号 |

串口下载的具体接线、BOOT0 设置、串口号和工具版本：

> 视频待核对：老师演示使用的具体下载器型号、串口下载接线方式、BOOT0/BOOT1 设置、下载工具和资料包路径。

以实际开发板原理图和 CubeMX 配置为准。

### MDK 输出文件的关系

```text
main.c / bsp_xxx.c
-> 编译生成 .o
-> 链接生成 .axf
-> 转换生成 .hex / .bin
-> DAP 或串口工具下载到 Flash
```

`.axf` 适合调试，`.hex` / `.bin` 适合下载和发布。PDF 的 MDK 编译章节明确提到 MDK 会围绕工程文件、输出文件和调试文件组织构建结果，但实际输出目录名由工程配置决定。

## CubeMX / MDK 配置

### MDK 安装和验证

1. 准备 MDK 安装包和 STM32F1 芯片包。
2. 安装 MDK，安装路径尽量使用纯英文目录。
3. 安装 STM32F1 Pack，让 MDK 能识别 STM32F103 系列芯片。
4. 打开课程示例工程或 CubeMX 生成的 `.uvprojx`。
5. 在 `Options for Target` 中确认芯片型号和 Flash 大小。
6. 在 `Output` 中确认是否生成 `.hex`，如果串口下载工具需要它就勾选。
7. 点击 Build，确认无缺失头文件、缺失 Pack、路径错误。

### DAP 下载配置

1. 连接 DAP 下载器到电脑。
2. 连接核心板 SWDIO、SWCLK、GND，必要时连接 3V3/VTref。
3. MDK 中打开 `Options for Target -> Debug`。
4. Debug adapter 选择 `CMSIS-DAP Debugger` 或课程对应的 DAP 选项。
5. 进入 `Settings`，确认能看到下载器序列号或设备信息。
6. 如果连接失败，尝试 `Connect under Reset`。
7. 在 `Utilities` 中确认下载算法和 Flash 编程设置。
8. 点击 Download，观察是否写入成功并自动复位运行。

### 串口下载验证

1. 确认 USB-TTL 和 STM32 共地。
2. USB-TTL 的 TX 接 STM32 RX，USB-TTL 的 RX 接 STM32 TX。
3. 按课程要求设置 BOOT0，使芯片从系统 Bootloader 启动。
4. 复位芯片。
5. 打开串口下载工具，选择正确串口号和固件文件。
6. 开始下载。
7. 下载完成后把 BOOT0 恢复为正常运行状态，再复位运行用户程序。

串口下载的 TX/RX 引脚和 BOOT0 操作方式以实际开发板原理图和 CubeMX 配置为准。

### CubeMX 安装和 HAL 库获取

1. 安装 STM32CubeMX。
2. 打开 CubeMX，确认网络或本地仓库能访问 STM32CubeF1 软件包。
3. 在 `Help -> Manage embedded software packages` 中检查 `STM32Cube MCU Package for STM32F1 Series`。
4. 如果课程使用离线包，先导入本地包，再确认版本。
5. 新建工程时选择正确芯片型号。
6. 生成 MDK 工程时，Toolchain/IDE 选择课程要求的 MDK 版本。
7. 用户代码只写在 `USER CODE BEGIN` 和 `USER CODE END` 之间。

这里不展开时钟树、PC13 LED 闪烁和完整 CubeMX 新建工程流程，这些内容已经放在 `01_准备与基础认知.md`。

## 最小代码

这一章的代码只用于验证“工程能编译、能下载、能运行”。不要把它当成外设实验模板。

### `Core/Src/main.c`

写在 `while (1)` 的 `USER CODE` 区域中：

```c
while (1)
{
    HAL_GPIO_TogglePin(GPIOC, GPIO_PIN_13);
    HAL_Delay(500);
}
```

常见前提：

- `MX_GPIO_Init()` 已被调用。
- PC13 已配置为 GPIO 输出。
- 板载 LED 是否低电平点亮，以实际开发板原理图和 CubeMX 配置为准。

### `Core/Src/main.c`

如果只想验证程序是否跑到主循环，可以先放一个断点或计数变量：

```c
uint32_t loop_count = 0;

while (1)
{
    loop_count++;
    HAL_Delay(100);
}
```

这个变量适合在 MDK Debug 的 Watch 窗口观察。若变量一直不变，先查下载、复位、启动模式和断点位置。

## 调试方法

按“硬件 -> 驱动/工具 -> 工程配置 -> 下载方式 -> 业务代码”的顺序排查。

### 硬件层

1. 核心板是否供电正常。
2. DAP 或 USB-TTL 是否被电脑识别。
3. GND 是否共地。
4. SWDIO/SWCLK 或 TX/RX 是否接对。
5. BOOT0 是否处在当前下载方式需要的状态。

### MDK 层

1. 工程能否 Build。
2. 是否缺 STM32F1 Pack。
3. Debug 是否选了正确下载器。
4. Flash Download 是否有正确算法。
5. 如果下载失败，尝试降低 SWD 速度或使用 `Connect under Reset`。

### CubeMX 层

1. 芯片型号是否选对。
2. HAL 包是否已安装。
3. Toolchain/IDE 是否选 MDK。
4. 生成代码后 `.uvprojx` 是否能打开。
5. 用户代码是否写在 `USER CODE` 区域。

### 常见坑

| 现象 | 常见原因 | 处理 |
|------|----------|------|
| MDK 找不到芯片 | 未安装 STM32F1 Pack | 安装对应芯片包 |
| Build 报路径错误 | 工程目录含特殊字符或路径过深 | 新手阶段用纯英文短路径 |
| DAP 识别不到芯片 | SWD 接线错、目标板未供电、BOOT/复位异常 | 查供电、GND、SWDIO/SWCLK、Reset |
| 串口下载失败 | TX/RX 接反、BOOT0 状态不对、串口号选错 | 交叉连接、复位进 Bootloader、重选端口 |
| 下载后不运行 | BOOT0 未恢复、未复位、程序跑飞 | BOOT0 置回正常运行，复位 |
| CubeMX 无法生成 HAL 工程 | HAL 包未安装或版本异常 | 检查软件包管理器 |

## 工程意义

后面每个 STM32 实验都依赖这一章的工具链闭环。如果环境没有跑通，后面看起来像“GPIO 不亮”“串口不通”“PWM 没波形”的问题，可能其实只是程序没下载进去、BOOT0 没恢复、DAP 没连上。

我以后做新工程，会先用最小程序确认：

```text
能编译
-> 能下载
-> 能复位运行
-> 能单步调试
-> 再开始配外设
```

## 易混淆点

| 容易混淆 | 正确理解 |
|----------|----------|
| MDK 和 CubeMX | MDK 负责编译/下载/调试，CubeMX 负责配置芯片并生成初始化代码 |
| DAP 下载和串口下载 | DAP 走 SWD，可调试；串口下载走 Bootloader，主要用于烧录 |
| `.uvprojx` 和 `.ioc` | `.uvprojx` 是 MDK 工程，`.ioc` 是 CubeMX 配置 |
| `.axf` 和 `.hex` | `.axf` 带调试信息，`.hex` 常用于下载 |
| 下载成功和程序正常运行 | 下载成功只说明写入 Flash，运行还受 BOOT0、复位、代码逻辑影响 |
| 安装 MDK 和安装芯片包 | MDK 是 IDE，芯片包让 IDE 认识具体 STM32 型号 |

## 我的理解

我现在把这一章理解成 STM32 学习的“地基检查”。如果地基没稳，后面所有外设现象都不可信。

以后新建或接手一个 STM32 工程，我会先按这个顺序检查：

```text
板子能上电
-> 下载器/串口能识别
-> MDK 能编译
-> 能下载
-> BOOT0 状态正确
-> 能进 main()
-> 再看外设
```

我不应该一开始就怀疑 HAL 函数或外设原理，很多问题其实是 Pack、下载器、BOOT0、路径和 `USER CODE` 区域这些基础问题。
