## 本质理解

RS485 不是一种新的 STM32 串口外设。我的理解是：

```text
STM32 USART
-> TX/RX TTL 电平
-> RS485 收发器
-> A/B 差分总线
-> 远端 RS485 收发器
-> 远端 UART
```

所以 RS485 程序的核心仍然是串口收发，只是多了一个“方向控制”：发送前把收发器切到发送，发送结束后再切回接收。

CAN 不是“高级串口”。CAN 更像一条共享消息总线：

```text
节点 A 发送 ID=0x100 的消息
节点 B、C、D 都能看到
谁接收由过滤器和业务逻辑决定
同时发送时由 ID 仲裁决定优先级
```

STM32F103 内部有 CAN 控制器，但仍需要外部 CAN 收发器把控制器信号转换为 CANH/CANL 差分总线信号。

> 视频待核对：RS485 收发器型号、DE/RE 方向控制引脚、CAN 收发器型号、CAN 波特率、过滤器配置、课程是否使用双板通信。

## 工作流程 / 原理

### RS485 半双工流程

```text
默认接收模式
-> 有数据要发
-> DE/RE 切到发送模式
-> UART 发送数据
-> 等待发送真正完成
-> DE/RE 切回接收模式
-> 等待对方回复
```

RS485 常见错误是 `HAL_UART_Transmit()` 返回后马上切方向，但最后一个字节可能还在移位寄存器里。稳妥做法是确认发送完成标志，或使用发送完成回调后再切回接收。

### CAN 发送流程

```text
配置 CAN 时钟和引脚
-> 配置过滤器
-> HAL_CAN_Start()
-> 打开接收通知
-> 填写 TxHeader
-> HAL_CAN_AddTxMessage()
-> 等待总线仲裁和发送完成
```

### CAN 接收流程

```text
总线上出现 CAN 帧
-> CAN 控制器按过滤器判断是否接收
-> 通过的消息进入 FIFO
-> 触发 FIFO0 消息挂起中断
-> 回调中 HAL_CAN_GetRxMessage()
-> 主循环或业务函数解析数据
```

CAN 调试的第一优先级是“总线能不能被 ACK”。如果只有一个节点在发，且没有其他节点应答，发送可能一直报错。

### `BSP/rs485.c`

```c
#include "rs485.h"
#include "usart.h"

#define RS485_UART_HANDLE      huart1
#define RS485_DE_GPIO_Port     GPIOA
#define RS485_DE_Pin           GPIO_PIN_8

void RS485_SetTxMode(void)
{
    /*
     * DE/RE 电平和是否共用一个控制脚，以实际收发器模块为准。
     */
    HAL_GPIO_WritePin(RS485_DE_GPIO_Port, RS485_DE_Pin, GPIO_PIN_SET);
}

void RS485_SetRxMode(void)
{
    HAL_GPIO_WritePin(RS485_DE_GPIO_Port, RS485_DE_Pin, GPIO_PIN_RESET);
}

HAL_StatusTypeDef RS485_Send(uint8_t *buf, uint16_t len)
{
    HAL_StatusTypeDef ret;

    RS485_SetTxMode();
    ret = HAL_UART_Transmit(&RS485_UART_HANDLE, buf, len, 1000);

    /*
     * 等待最后一个字节真正发送完成后再切回接收。
     * 具体标志和句柄名按 CubeMX 实际生成名称调整。
     */
    while (__HAL_UART_GET_FLAG(&RS485_UART_HANDLE, UART_FLAG_TC) == RESET)
    {
    }

    RS485_SetRxMode();
    return ret;
}

HAL_StatusTypeDef RS485_StartReceive(uint8_t *buf, uint16_t len)
{
    RS485_SetRxMode();
    return HAL_UART_Receive_IT(&RS485_UART_HANDLE, buf, len);
}
```

### `BSP/can_bus.c`

```c
#include "can_bus.h"
#include "can.h"

#define CAN_BUS_HANDLE hcan

HAL_StatusTypeDef CAN_BusInit(void)
{
    CAN_FilterTypeDef filter;
    HAL_StatusTypeDef ret;

    /*
     * 过滤器参数仅为框架。
     * 过滤器组号、模式、掩码、FIFO 和 ID 范围以课程配置为准。
     */
    filter.FilterBank = 0;
    filter.FilterMode = CAN_FILTERMODE_IDMASK;
    filter.FilterScale = CAN_FILTERSCALE_32BIT;
    filter.FilterIdHigh = 0x0000;
    filter.FilterIdLow = 0x0000;
    filter.FilterMaskIdHigh = 0x0000;
    filter.FilterMaskIdLow = 0x0000;
    filter.FilterFIFOAssignment = CAN_RX_FIFO0;
    filter.FilterActivation = ENABLE;

    ret = HAL_CAN_ConfigFilter(&CAN_BUS_HANDLE, &filter);
    if (ret != HAL_OK)
    {
        return ret;
    }

    ret = HAL_CAN_Start(&CAN_BUS_HANDLE);
    if (ret != HAL_OK)
    {
        return ret;
    }

    return HAL_CAN_ActivateNotification(&CAN_BUS_HANDLE, CAN_IT_RX_FIFO0_MSG_PENDING);
}

HAL_StatusTypeDef CAN_SendStdFrame(uint16_t std_id, uint8_t *data, uint8_t len)
{
    CAN_TxHeaderTypeDef tx_header;
    uint32_t mailbox;

    if (len > 8)
    {
        len = 8;
    }

    tx_header.StdId = std_id;
    tx_header.ExtId = 0;
    tx_header.IDE = CAN_ID_STD;
    tx_header.RTR = CAN_RTR_DATA;
    tx_header.DLC = len;
    tx_header.TransmitGlobalTime = DISABLE;

    return HAL_CAN_AddTxMessage(&CAN_BUS_HANDLE, &tx_header, data, &mailbox);
}

void HAL_CAN_RxFifo0MsgPendingCallback(CAN_HandleTypeDef *hcan)
{
    CAN_RxHeaderTypeDef rx_header;
    uint8_t rx_data[8];

    if (hcan == &CAN_BUS_HANDLE)
    {
        if (HAL_CAN_GetRxMessage(hcan, CAN_RX_FIFO0, &rx_header, rx_data) == HAL_OK)
        {
            CAN_ProcessRxMessage(&rx_header, rx_data);
        }
    }
}

void CAN_ProcessRxMessage(CAN_RxHeaderTypeDef *header, uint8_t *data)
{
    /*
     * 根据 StdId/ExtId、DLC 和 data 解析业务命令。
     * 不确定具体协议时，先串口打印 ID 和数据。
     */
    (void)header;
    (void)data;
}
```

## 调试方法

### 供电

- RS485/CAN 收发器模块供电先确认，不要默认和 STM32 完全一致。
- ESP、舵机、电机等大电流模块同时存在时，通信异常可能来自供电波动。

### 共地

- RS485、CAN 调试板、USB 串口工具、外部电源需要共同参考地。
- 差分总线抗干扰不等于完全不需要参考地，实际工程要按布线和隔离方案确认。

### 接线

- RS485 A/B 线、CANH/CANL 接反都会导致通信失败。
- STM32 到收发器的 TX/RX、CAN_TX/CAN_RX 也要核对方向。
- 收发器型号、引脚、接线方式：以实际开发板原理图和 CubeMX 配置为准。

### 收发器方向 / 终端电阻

- RS485 半双工发送前切发送，发送完成后切接收。
- DE/RE 有效电平不能凭经验写死。
- RS485 和 CAN 长线或多节点时要关注终端电阻、偏置电阻、屏蔽线和总线拓扑。

### CubeMX 配置

- RS485 先确认 USART 波特率、TX/RX 引脚、NVIC/DMA 是否与代码一致。
- CAN 先确认波特率、采样点、过滤器、NVIC 和引脚复用。
- CAN 双板实验时，两端位时序必须一致。

### HAL API 返回值

- RS485 先检查 `HAL_UART_Transmit()` 和接收启动函数返回值。
- CAN 先检查 `HAL_CAN_ConfigFilter()`、`HAL_CAN_Start()`、`HAL_CAN_AddTxMessage()` 返回值。
- CAN 发不出时查看错误码和发送邮箱状态。

### 串口打印 / 逻辑分析仪 / CAN 分析仪

- RS485 可用串口打印方向切换、发送长度和收到的原始字节。
- 逻辑分析仪看 UART TX/RX 和 DE/RE 时序是否匹配。
- CAN 优先用 CAN 分析仪或 USB-CAN 看总线上是否有帧、是否 ACK、ID 是否正确。

### 协议帧格式

- RS485 本身只管物理层，真正的数据帧格式由上层协议决定。
- CAN 帧需要看 ID、IDE、RTR、DLC 和数据区。
- 不确定课程协议时，先记录原始帧，不要直接写复杂解析。

### 业务逻辑

- 如果底层帧都收不到，不要先改业务命令。
- 如果底层帧能收到但控制不生效，再查 ID、命令字、数据长度和执行分支。

## 工程意义

RS485 适合把普通串口扩展到更远距离、更强抗干扰的现场通信。很多仪表、传感器、变频器和 PLC 都会用 RS485 作为物理层。

CAN 适合多节点、强实时、强仲裁的控制网络。学会 CAN 后，后续理解汽车电子、工业设备、机器人多控制器通信会更顺。

## 易混淆点

| 容易混淆 | 正确理解 |
|----------|----------|
| RS485 是一种新串口协议 | RS485 主要是物理层，STM32 侧仍常用 USART/UART |
| RS485 可以同时收发 | 常见模块是半双工，需要方向控制 |
| DE/RE 电平固定 | 不同收发器和模块接法可能不同，要看原理图 |
| 差分总线不需要共地 | 实际工程仍要考虑参考地、隔离和共模范围 |
| CAN 和 UART 差不多 | CAN 是多节点总线，靠 ID 仲裁和过滤器 |
| CAN ID 是节点地址 | CAN ID 更像消息优先级和消息类型，不等于固定节点地址 |
| CAN 只要一个节点就能发 | 没有其他节点 ACK 时可能发送失败 |
| 过滤器越严格越好 | 初期调试可先放宽过滤器，确认能收到后再收窄 |

## 我的理解

我现在把 RS485 理解成“给串口换了一副适合远距离的差分外壳”。代码还是串口代码，但工程上多了收发器、A/B 线、方向控制和终端匹配。

我现在把 CAN 理解成“一群节点在同一条线上按 ID 说话”。它不是点对点串口，谁能发、谁先发、谁收得到，都和 ID、仲裁、过滤器、ACK 有关。

以后调 RS485/CAN，我会先看物理层有没有帧，再看 HAL 返回值，最后才看业务协议。不要在 A/B 或 CANH/CANL 都没确认时纠结命令格式。

## [40] RS485应用

> 视频待核对：RS485 收发器型号、DE/RE 引脚、波特率、协议、终端电阻、偏置电阻和是否双板实验。

### 实验定位

RS485 可以理解为 UART 外面加了一层差分半双工收发器。PDF 的 USART 章节只能支撑串口底层，不能凭空补完整 RS485 模块实验。

### 工作流程

```text
默认接收模式
-> 发送前拉 DE/RE 到发送方向
-> UART 发送数据
-> 等待发送完成
-> 切回接收方向
-> 等待对方响应
```

### 硬件检查

- A/B 总线不能随意和 TX/RX 混淆。
- 多节点总线要考虑终端电阻和偏置。
- 两端设备需要共地或满足课程模块要求。
- DE/RE 方向控制引脚以实际开发板原理图和 CubeMX 配置为准。

### 调试方法

- 先短接或双板验证普通 UART 是否通。
- 再加 RS485 收发器和方向控制。
- 发送后必须切回接收，否则收不到对方数据。
- 用逻辑分析仪同时看 UART TX 和 DE/RE 最容易定位问题。

### 常见坑

- DE/RE 方向反。
- 发送完成前过早切回接收。
- A/B 接反。
- 没有终端电阻或偏置导致总线空闲不稳定。

### 实验定位

CAN 实验至少包含 STM32 内部 CAN 控制器、外部 CAN 收发器、CANH/CANL 总线、波特率位时序、过滤器和收发双方协议。没有视频细节时，只能写框架和调试路径。

### 核心概念

| 名词 | 工程含义 |
|------|----------|
| CAN 控制器 | STM32 内部外设，负责帧、仲裁、邮箱、FIFO、过滤器 |
| CAN 收发器 | 把 MCU 逻辑电平转换成 CANH/CANL 差分信号 |
| 标准帧 / 扩展帧 | ID 位数不同，收发双方必须一致 |
| ID 仲裁 | 总线上多个节点同时发送时，ID 决定优先级 |
| 发送邮箱 | HAL 发送帧时放入的硬件发送槽 |
| 接收 FIFO | 通过过滤器的帧进入接收 FIFO |
| 过滤器 | 决定哪些 ID 可以被接收 |

### 调试方法

- 先确认 CAN 收发器供电、共地、CANH/CANL 和终端电阻。
- 两端波特率和采样点必须一致。
- 过滤器先放宽验证能收，再收紧到课程 ID。
- 有条件时用 CAN 分析仪确认总线上是否有帧。

### 常见坑

- 只有 STM32 CAN 引脚，没有外接 CAN 收发器。
- 过滤器配置太窄导致收不到。
- 双板波特率不一致。
- CANH/CANL 接反或没有终端电阻。
