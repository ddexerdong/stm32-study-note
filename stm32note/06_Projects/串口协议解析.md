# 串口协议解析

> 项目目标：把 UART 字节流稳定地还原成完整、可验证的业务帧。
>
> 原始来源：[[04_串口与DMA]]。

## 分层

```text
UART/RS485 接收
-> DMA/中断缓冲区
-> 帧边界检测
-> 帧头和长度校验
-> 校验和/CRC
-> 命令与字段解析
-> 业务分发
```

## 必须处理的问题

- 粘包：一次收到多帧。
- 半包：一帧分多次收到。
- 噪声：帧头前存在无效字节。
- 超时：帧长时间不完整。
- 缓冲区溢出：生产速度高于消费速度。

## 状态机思路

按“找帧头 -> 读固定头 -> 得到长度 -> 等完整帧 -> 校验 -> 分发”处理。IDLE 只能提示总线暂时空闲，不能替代协议长度和校验。

> 视频待核对：课程雷达模块的型号、波特率、帧头、长度、字段和校验方式。

## 本节目标

- 能设计带长度、命令、载荷和校验的帧格式。
- 能用状态机处理半包、粘包、超时和错误恢复。
- 能把 IDLE + DMA 接收与业务命令分发解耦。

## 知识地图

| 问题 | 工程含义 |
|---|---|
| 半包 | 一帧分多次到达 |
| 粘包 | 多帧一次到达 |
| 帧头 | 从噪声中定位候选帧 |
| 长度 | 判断完整帧边界 |
| 命令字 | 决定 payload 解释方式 |
| 校验 | 拒绝传输错误或错位 |
| 超时 | 放弃长期不完整帧 |

## 本质理解

UART/DMA 回调只告诉你“收到一些字节”，不会保证正好一帧。协议解析器必须是持续消费字节流的状态机，能跨回调保留状态，也能在错误后重新找帧头。

## 推荐帧格式

```text
SOF | Version | Command | Length | Payload | Checksum/CRC
```

长度和校验算法必须由协议明确，不能由接收次数推断。

## CubeMX 与接收链

1. USART 配置波特率/8N1。
2. RX DMA 设合适模式和缓冲长度。
3. 使用 IDLE/RxEvent 把新字节送入 ring buffer。
4. 解析器在主循环持续取字节。

## 状态机框架

> 代码性质：伪代码，用于说明业务逻辑。

```c
switch (parser.state) {
case FIND_SOF:  FindFrameHeader(byte); break;
case READ_HEAD: ReadFixedHeader(byte); break;
case READ_BODY: ReadPayloadUntilLength(byte); break;
case READ_CRC:  ValidateAndDispatch(byte); break;
}
```

## 命令分发

LED、蜂鸣器、舵机命令先验证长度和参数范围，再设置业务请求；不要在 UART 回调里直接执行长动作。

## 调试顺序

```text
保存原始 HEX
-> 单帧
-> 分片输入
-> 多帧粘连
-> 错误校验
-> 噪声前缀
-> 超时恢复
-> 长时间压力测试
```

## 常见坑

| 坑 | 后果 | 修复 |
|---|---|---|
| 一次 IDLE=一帧 | 半包时误解析 | 按长度和状态机 |
| `strlen` 处理二进制 | 遇 0 截断 | 始终显式长度 |
| 无边界检查 | 缓冲区溢出 | 检查最大 payload |
| 校验前执行业务 | 错帧触发动作 | 验证后分发 |
| 错误后不复位 | 后续全乱 | 重新搜索帧头 |
