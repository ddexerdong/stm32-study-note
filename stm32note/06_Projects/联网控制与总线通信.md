# 联网控制与总线通信

> 项目目标：组合传感器、执行器和通信链路，建立可观察、可恢复的业务状态机。

## 数据上报

```text
采集 DHT11 / ADC
-> 校验数据有效性
-> 格式化应用层消息
-> ESP8266/RS485/CAN 发送
-> 等待结果或超时
-> 记录状态
```

## 远程控制

```text
接收字节/帧
-> 协议解析
-> 权限与参数校验
-> 分发到 LED/蜂鸣器/舵机
-> 返回执行结果
```

## 工程原则

- 通信层和业务层分离。
- 不在回调中执行长时间动作。
- 每条命令有明确格式、超时和失败响应。
- 网络、RS485 和 CAN 的物理参数必须单独验证。

> 视频待核对：ESP8266 AT 参数和透传步骤、RS485 双板协议、CAN 位时序/过滤器/消息 ID，以及课程具体控制协议。

## 本节目标

- 能统一抽象 ESP8266、RS485 和 CAN 的传输适配层。
- 能设计数据上报、远程控制、超时和恢复状态。
- 能逐层验证物理链路、帧协议和业务动作。

## 知识地图

| 链路 | 物理/传输层 | 应用层职责 |
|---|---|---|
| ESP8266 | UART + WiFi/TCP/UDP | 上报、控制协议、重连 |
| RS485 | UART + 差分半双工 | 节点地址、轮询、校验 |
| CAN | CAN 控制器 + 收发器 | 消息 ID、信号定义、周期 |

## 本质理解

三种链路的物理机制不同，但工程上都需要统一的数据模型、帧定义、超时、错误状态和可观察日志。项目不应把 AT 字符串、RS485 方向脚和 CAN 邮箱直接混在业务逻辑中。

## 系统组成

```text
Sensors/Actuators
-> App 数据模型
-> Protocol Codec
-> ESP8266 / RS485 / CAN Adapter
-> 物理网络
```

## CubeMX 配置

- ESP8266/RS485：USART，可选 IDLE + DMA；RS485 增加 DE/RE GPIO。
- CAN：CAN 引脚、位时序、过滤器、接收通知。
- 日志串口与业务串口尽量分离。
- 所有波特率和引脚按原理图/视频/手册。

## 本项目使用的 HAL 层

### API 速查

| 传输动作 | HAL 函数 |
|---|---|
| ESP8266 发送命令/数据 | `HAL_UART_Transmit()` / `HAL_UART_Transmit_DMA()` |
| ESP8266/RS485 不定长接收 | `HAL_UARTEx_ReceiveToIdle_DMA()` |
| RS485 方向控制 | `HAL_GPIO_WritePin()` |
| CAN 配置/启动 | `HAL_CAN_ConfigFilter()` + `HAL_CAN_Start()` |
| CAN 发送 | `HAL_CAN_AddTxMessage()` |
| CAN 接收 | `HAL_CAN_ActivateNotification()` + FIFO 回调 + `HAL_CAN_GetRxMessage()` |
| 超时/重连节拍 | `HAL_GetTick()` |

### 使用注意

| HAL 函数 | 前置条件与调用位置 | 返回值 / 阻塞 | 常见坑 |
|---|---|---|---|
| `HAL_UART_Transmit()` / `HAL_UART_Transmit_DMA()` | UART 参数和模块固件已确认，在传输适配层调用 | 阻塞或非阻塞，均检查状态 | 把 AT 状态机写进业务层；DMA buffer 提前复用 |
| `HAL_UARTEx_ReceiveToIdle_DMA()` | DMA/IDLE/ring buffer 已配置 | 非阻塞 | IDLE 当帧边界；回调中直接控制执行器 |
| `HAL_GPIO_WritePin()` | DE/RE 有效电平已按原理图确认 | `void`；非阻塞 | 最后停止位未发完就切回接收 |
| `HAL_CAN_ConfigFilter()` + `HAL_CAN_Start()` | 位时序、收发器、过滤器已设计 | 返回状态；非阻塞启动 | 未配置过滤器或双方位时序不同 |
| `HAL_CAN_AddTxMessage()` | CAN 已启动且有邮箱 | 入邮箱非阻塞 | `HAL_OK` 不等于总线已 ACK |
| `HAL_CAN_ActivateNotification()` + FIFO 回调 + `HAL_CAN_GetRxMessage()` | NVIC 和通知已启用 | 回调中同步取帧 | 回调不取帧导致 FIFO 堆积 |
| `HAL_GetTick()` | 状态机维护截止时间 | 非阻塞 | 使用长 `HAL_Delay()` 卡住其它链路 |

### 典型调用顺序

```text
分别完成 ESP8266 UART、RS485 UART+方向脚、CAN 的独立回环/双节点验证
-> 每条链路封装统一 Send/Poll/Recover 接口
-> 回调只把字节或帧投入队列
-> App 状态机执行协议解析、数据上报和控制命令
-> HAL_GetTick() 处理超时、重连和故障恢复
```

### 什么时候用哪个函数？

| 场景 | 推荐函数 |
|---|---|
| ESP8266/RS485 不定长字节流 | UART IDLE + DMA + ring buffer |
| RS485 发送方向切换 | GPIO DE/RE + UART TC/发送完成事件 |
| CAN 发送消息 | `HAL_CAN_AddTxMessage()`，并监控错误和邮箱状态 |
| CAN 中断接收 | Notification + FIFO Callback + `HAL_CAN_GetRxMessage()` |
| 跨链路业务超时 | `HAL_GetTick()` 驱动的非阻塞状态机 |

## 核心框架

> 代码性质：伪代码，用于说明业务逻辑，不是可直接编译代码。

```c
typedef enum
{
    TRANSPORT_ESP8266 = 0,
    TRANSPORT_RS485,
    TRANSPORT_CAN
} TransportType_t;

typedef struct
{
    uint8_t version;
    uint16_t message_id;
    uint16_t payload_length;
    uint8_t payload[NETWORK_MAX_PAYLOAD];
} UnifiedMessage_t;

#if COMMUNICATION_DEBUG_ENABLED
#define COMM_DEBUG(...) Debug_Print(__VA_ARGS__)
#else
#define COMM_DEBUG(...) ((void)0)
#endif

static uint8_t Transport_Send(TransportType_t type,
                              const UnifiedMessage_t *message)
{
    uint8_t frame[TRANSPORT_FRAME_MAX_SIZE];
    uint16_t length = Protocol_Encode(message, frame, sizeof(frame));
    if (length == 0U) return 0U;

    if (type == TRANSPORT_ESP8266)
        return ESP8266_SendPayload(frame, length);
    if (type == TRANSPORT_RS485)
        return RS485_SendFrame(frame, length);
    if (type == TRANSPORT_CAN)
        return CAN_SendUnifiedMessage(message);
    return 0U;
}

static void Communication_OnDownlink(const uint8_t *data, uint16_t length)
{
    UnifiedMessage_t message;
    if (Protocol_Decode(data, length, &message))
    {
        App_DispatchRemoteCommand(&message);
    }
}

void HAL_CAN_RxFifo0MsgPendingCallback(CAN_HandleTypeDef *hcan)
{
    CAN_RxHeaderTypeDef header;
    uint8_t data[CAN_CLASSIC_MAX_DATA_BYTES];
    if ((hcan->Instance == CAN1) &&
        (HAL_CAN_GetRxMessage(hcan, CAN_RX_FIFO0, &header, data) == HAL_OK))
    {
        CAN_ReassembleAndDispatch(&header, data);
    }
}

void Communication_Task(void)
{
    CollectIncomingFrames();
    ESP8266_PollDownlink(Communication_OnDownlink);
    RS485_PollDownlink(Communication_OnDownlink);

    if (TimeToPublish())
    {
        UnifiedMessage_t message;
        if (BuildTelemetry(&snapshot, &message))
        {
            (void)Transport_Send(TRANSPORT_ESP8266, &message);
            (void)Transport_Send(TRANSPORT_RS485, &message);
            (void)Transport_Send(TRANSPORT_CAN, &message);
        }
    }

    Transport_HandleTimeoutAndReconnect();
    COMM_DEBUG("communication state updated\r\n");
}
```

统一结构只定义应用消息，不意味着三种链路使用相同帧大小。ESP8266 AT/网络协议、RS485 节点帧、CAN 分片与 ID 映射必须分别按项目协议和实测实现。

```text
单一传输链路回环
-> 固定测试帧
-> 协议编码/解码
-> 传感器上报

-> 断线/冲突/超时

```

## 常见坑

| 坑 | 处理 |
|---|---|
| 通信回调直接控制硬件 | 转成 App 命令事件 |
| 网络断线卡死主循环 | 使用状态机和超时 |
| RS485 多节点同时发 | 设计主从或令牌机制 |
| CAN 过滤器过窄 | 先全收验证再收紧 |
| 不同链路协议不一致 | 统一消息模型和编解码 |
| 日志影响实时通信 | 限制日志或独立串口 |

## 待核对项

ESP8266 固件/AT/透传、RS485 收发器/协议、CAN 位时序/过滤器/ID 都必须按实际系统确认。
